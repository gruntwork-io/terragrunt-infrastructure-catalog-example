# Adopting Terragrunt 1.1 features

Terragrunt 1.1 introduced three features that change how a catalog like this one is authored:

- [`update_source_with_cas`](https://docs.terragrunt.com/features/cas/): reference in-repo modules and units by relative path instead of a remote Git URL with a pinned `ref`.
- [`autoinclude`](https://docs.terragrunt.com/reference/experiments/#stack-dependencies): declare a stack's dependency wiring in the stack, instead of threading dependency paths through `values` and declaring `dependency` blocks in every unit.
- [`mark_glob_as_read`](https://docs.terragrunt.com/reference/hcl/functions/#mark_glob_as_read): mark application source that a unit packages through a hook or `run_cmd`, so changes to it cascade to the unit under reading-based filters.

This guide walks through adopting them in an existing catalog. The units and stacks in this repository are the finished result, so refer to them for complete examples as you go.

## Prerequisites

You need **Terragrunt 1.1 or newer**. Bump the pinned version (here, in [`mise.toml`](/mise.toml)) and document the minimum in your README.

## Step 1: Reference in-repo modules by relative path with `update_source_with_cas`

Before 1.1, a catalog unit had to point `source` at a remote Git URL with a `?ref=` even for a module in the same repository. Units and stacks are materialized as shallow directories when consumed, so a plain relative path wouldn't resolve from the generated location. The only option was a remote URL with a `version` value threaded through to fill the `ref`.

#### Before

```hcl
# units/mysql/terragrunt.hcl
terraform {
  source = "github.com/acme/catalog//modules/mysql?ref=${values.version}"
}
```

Set `update_source_with_cas = true` and replace the URL with a path relative to the repository root. The `//` separates the repository root from the subdirectory, exactly as in any Terragrunt source. At generation time Terragrunt clones the repo once via CAS and rewrites the source to a deterministic `cas::sha256:...//modules/mysql` reference.

#### After

```hcl
# units/mysql/terragrunt.hcl
terraform {
  source                 = "../..//modules/mysql"
  update_source_with_cas = true
}
```

A few rules to keep in mind:

- **The source must be a literal string.** Interpolation, function calls, and `local.*`/`values.*` references are rejected. This is what lets the `version` plumbing go away entirely.
- **The path must be relative and stay inside the repository.** Absolute paths and paths that escape the repository root are rejected.
- Apply the same change to a stack's `unit`/`stack` sources (`source = "../..//units/<name>"`). The attribute is valid on `unit`, `stack`, and `terraform` blocks.

### How consumers reference the catalog

Consumers of the catalog do **not** set `update_source_with_cas`. The attribute only has an effect inside catalog files, where it flags a nested source for rewriting. There are two ways a consumer references the catalog, and CAS handles both without the attribute:

- **Remotely**, the normal case for a real `infrastructure-live` repository: `source = "github.com/acme/catalog//stacks/<name>?ref=v1.0.0"`. CAS is applied automatically for remote sources.
- **By local path**, as the in-repo [examples](/examples/terragrunt/stacks) do so they can test the catalog without a release. Use the `//` separator to mark the repository root so CAS can find it and rewrite the nested catalog sources:

  ```hcl
  unit "service" {
    source = "../../../..//units/ec2-asg-stateful-service"
    path   = "service"
    # ...
  }
  ```

  Without the `//`, the unit is copied verbatim and its relative module source is left unrewritten, so it fails to resolve from the generated location.

## Step 2: Wire stack dependencies with `autoinclude`

Before 1.1, a stack passed dependency paths to its units through `values`, and each unit declared `dependency` blocks pointing at `values.<x>_path`.

#### Before

```hcl
# stack
unit "service" {
  source = "..."

  values = {
    db_path     = "../db"
    asg_sg_path = "../sgs/asg"
    # ...
  }
}

# units/ec2-asg-stateful-service/terragrunt.hcl
dependency "db" {
  config_path = values.db_path
  # ...
}

dependency "asg_sg" {
  config_path = values.asg_sg_path
  # ...
}

inputs = {
  asg_sg_id = dependency.asg_sg.outputs.id
  # ...
}
```

With `autoinclude`, declare that wiring in the stack. The block generates a `terragrunt.autoinclude.hcl` next to the unit and is merged into it at parse time. Reference sibling components by `unit.<name>.path` (or `stack.<name>.path` for a nested stack), which is resolved to a relative path at generation time.

#### After

```hcl
# stack
unit "service" {
  source                 = "../..//units/ec2-asg-stateful-service"
  update_source_with_cas = true
  path                   = "service"

  values = {
    /* unit-intrinsic values only, no *_path or version */
  }

  autoinclude {
    dependency "asg_sg" {
      config_path = unit.asg_sg.path

      mock_outputs = {
        id = "mock-asg-sg-id"
      }
    }

    dependency "db" {
      config_path = unit.db.path

      mock_outputs = {
        endpoint = "mock-endpoint"
        db_name  = "mock-db-name"
      }
    }

    inputs = {
      asg_sg_id = dependency.asg_sg.outputs.id
    }
  }
}
```

### Decide what moves into `autoinclude` and what stays in the unit

`autoinclude` is merged into the unit with Terragrunt's default (shallow) strategy, so the unit can keep its own `inputs` while the `autoinclude` block contributes more; if both set the same input key, the `autoinclude` value wins. Use that to move **only the input logic that's specific to the unit's place within the stack** (the pure cross-unit dependency passthroughs) and leave everything intrinsic to the unit where it is:

- **Move to `autoinclude`:** the `dependency` blocks, and inputs whose value is entirely a dependency output (for example `asg_sg_id = dependency.asg_sg.outputs.id`, or a security-group rule whose every input is dependency-derived).
- **Keep in the unit:** inputs that render the unit's own assets (a `templatefile()` of a script in the unit, a `run_cmd()` that hashes the unit's `src/`, an IAM policy document). A unit's own `inputs` and `terraform` hooks can read an `autoinclude`-injected `dependency.<name>.outputs` value, so the dependency declaration lives in the stack while the consumption stays beside the asset it configures.

See [`units/ec2-asg-stateful-service`](/units/ec2-asg-stateful-service/terragrunt.hcl) and [`stacks/ec2-asg-stateful-service`](/stacks/ec2-asg-stateful-service/terragrunt.stack.hcl) for a worked example of this split, and [`units/sg-to-db-sg-rule`](/units/sg-to-db-sg-rule/terragrunt.hcl) for a unit that is pure wiring and declares nothing locally.

## Step 3: Track application source with `mark_glob_as_read`

When a unit packages application source through a hook or `run_cmd` instead of reading it with a native Terragrunt function, Terragrunt has no way to know the unit depends on those files. Call `mark_glob_as_read` from a `locals` block to record them, so a change to the source cascades to the unit under reading-based filters such as `terragrunt run --all --filter 'reading=...'`:

```hcl
# units/ecs-fargate-stateful-service/terragrunt.hcl
locals {
  src_dir   = "${get_terragrunt_dir()}/src"
  src_files = mark_glob_as_read("${local.src_dir}/{*,**/*}")
}
```

- **Call it from `locals`, not `inputs`.** During a `run --all`, the queue is populated before `inputs` is evaluated, so a call in `inputs` is too late to influence which units run.
- **Match every depth with `{*,**/*}`.** A bare `**/*` skips files directly in the directory; the brace alternation catches both the top level and nested files.

In this catalog the three units that package a local `./src` use it: [`ecs-fargate-stateful-service`](/units/ecs-fargate-stateful-service/terragrunt.hcl), [`lambda-stateful-service`](/units/lambda-stateful-service/terragrunt.hcl), and [`js-lambda-stateful-service`](/units/js-lambda-stateful-service/terragrunt.hcl).
