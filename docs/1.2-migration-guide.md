# Adopting Terragrunt 1.2 features

Terragrunt 1.2 makes two features in stack files generally available:

- The [`expansion`](https://docs.terragrunt.com/reference/hcl/blocks#expansion) block, which repeats a `stack`, `unit` or `dependency` block once per element of a `for_each` or `count`.
- The `enabled` attribute on [`unit`](https://docs.terragrunt.com/reference/hcl/blocks#unit) and [`stack`](https://docs.terragrunt.com/reference/hcl/blocks#stack) blocks, which skips the component during stack generation when it is `false`.

This guide walks through where this catalog uses each one, and how to adopt them in your own catalog. The stacks and examples in this repository are the finished result, so refer to them for complete configurations as you go.

## Prerequisites

You need **Terragrunt 1.2 or newer**. Bump the pinned version (here, in [`mise.toml`](/mise.toml)) and document the minimum in your README.

If you tried these features on 1.1 behind the `block-iteration` experiment, drop `--experiment block-iteration` and `TG_EXPERIMENT=block-iteration` from your scripts and CI. 1.2 no longer requires either.

## Repeat a stack per environment with `for_each` / `count`

A live stack that deploys the same catalog stack to several environments repeats the whole `stack` block for each one, even though only a few values differ.

#### Before

```hcl
stack "non_prod" {
  source = "../../../..//stacks/ec2-asg-stateful-service"
  path   = "non-prod"

  values = {
    name              = "multi-env-asg-non-prod"
    min_size          = 2
    max_size          = 3
    allocated_storage = 50
    # ...every other value, repeated
  }
}

stack "prod" {
  source = "../../../..//stacks/ec2-asg-stateful-service"
  path   = "prod"

  values = {
    name              = "multi-env-asg-prod"
    min_size          = 3
    max_size          = 5
    allocated_storage = 100
    # ...every other value, repeated
  }
}
```

If you want, you can now move the values that differ into a map, and expand one `stack` block over it. Inside the block, `each.key` is the map key and `each.value` is its value.

#### After

```hcl
locals {
  environments = {
    "non-prod" = { min_size = 2, max_size = 3, allocated_storage = 50 }
    "prod"     = { min_size = 3, max_size = 5, allocated_storage = 100 }
  }
}

stack "environment" {
  expansion {
    for_each = local.environments
  }

  source = "../../../..//stacks/ec2-asg-stateful-service"
  path   = each.key

  values = {
    name              = "multi-env-asg-${each.key}"
    min_size          = each.value.min_size
    max_size          = each.value.max_size
    allocated_storage = each.value.allocated_storage
    # ...values shared by every environment, written once
  }
}
```

See [`examples/terragrunt/stacks/multi-env-stateful-asg-services`](/examples/terragrunt/stacks/multi-env-stateful-asg-services/terragrunt.stack.hcl) for the full stack.

This won't require any state manipulation if you keep the value of `path` the same. From OpenTofu's perspective, nothing has changed here. The same Terragrunt units are being generated at the same paths, with the same state keys.

Output addresses change as a consequence of this, however. `terragrunt stack output` nests each element under its key, so `non_prod.service.url` becomes `environment["non-prod"].service.url`. Update any scripts or tests that read stack outputs.

## Repeat units inside a stack with `for_each` / `count`

The same applies to `unit` blocks. [`examples/terragrunt/stacks/shared-db-asg-services`](/examples/terragrunt/stacks/shared-db-asg-services/terragrunt.stack.hcl) deploys several ASG security groups connected to one MySQL database. Each service needs its own security group and its own rule allowing that group to reach the database:

```hcl
locals {
  services = {
    api = { min_size = 2, max_size = 4 }
    web = { min_size = 1, max_size = 2 }
  }
}

# ...

unit "asg_sg" {
  expansion {
    for_each = local.services
  }

  source = "../../../..//units/sg"
  path   = "sgs/${each.key}"

  values = {
    name = "shared-db-asg-${each.key}-asg-sg"
  }
}

# ...

unit "service" {
  expansion {
    for_each = local.services
  }

  source = "../../../..//units/ec2-asg-stateful-service"
  path   = "services/${each.key}"

  # ...

  autoinclude {
    dependency "asg_sg" {
      config_path = unit.asg_sg[each.key].path
    }

    dependency "db" {
      config_path = unit.db.path
    }

    # ...
  }
}

# ...
```

You can reference individual elements from an expanded unit by using its key (e.g. `unit.asg_sg[each.key].path`. Because `service` and `asg_sg` expand over the same map, `each.key` in `service` always names an `asg_sg` element that exists.


### Accessing dependency outputs

You can access outputs from an expanded dependency how you likely expect, by interacting with the map exposed from the map of expanded instances:

```hcl
unit "dashboard" {
  # ...

  autoinclude {
    dependency "service" {
      expansion {
        for_each = local.services
      }

      config_path = unit.service[each.key].path
    }

    inputs = {
      service_urls = { for name, service in dependency.service : name => service.outputs.url }
    }
  }
}
```

## Make a component optional with `enabled`

A catalog stack can have a component that only some consumers want, such as monitoring that only production needs. Set `enabled` from a value, and the stack generates that component only when it is `true`.

[`stacks/ec2-asg-stateful-service`](/stacks/ec2-asg-stateful-service/terragrunt.stack.hcl) accepts an optional `enable_alarms` value. When it is `true`, the stack generates an `alarms` unit with CloudWatch alarms on the service's ALB, which notify an SNS topic:

```hcl
unit "alarms" {
  enabled = try(values.enable_alarms, false)

  source                 = "../..//units/alb-alarms"
  update_source_with_cas = true
  path                   = "alarms"

  autoinclude {
    dependency "service" {
      config_path = unit.service.path
    }

    inputs = {
      alb_arn_suffix          = dependency.service.outputs.alb_arn_suffix
      target_group_arn_suffix = dependency.service.outputs.target_group_arn_suffix
    }
  }
}
```

Consumers that don't set the value get the same units they got before, so adding an optional component this way is a backwards-compatible change to the catalog. The multi-environment example turns alarms on for prod only.

Disabling a component only stops Terragrunt from generating it. Infrastructure that was already deployed stays deployed, so destroy the component before you disable it. See [Lifecycle](#lifecycle).

## When to use `count`

`expansion` also accepts `count`, with `count.index` as the zero-based position of each element. This catalog doesn't use it, because no component here is a set of interchangeable copies.

In general, prefer to use `for_each` instead of `count` unless all the elements of your expansion are interchangable. `count` keys elements by position. Removing an element from the middle shifts every element after it, so OpenTofu plans to change the shifted units into their neighbours and leaves the last one orphaned. Use `count` only when the elements are identical and you only ever add or remove at the end:

```hcl
unit "worker" {
  expansion {
    count = 3
  }

  source = "../../../..//units/worker"
  path   = "workers/${count.index}"
}
```

For a component that is either present or absent, use `enabled` instead of `count`. `count = local.create ? 1 : 0` renames the component to `worker[0]` when it is present, which changes its output address and forces consumers to adopt that change.

To learn how to handle the lifecycle of units being added and removed due to expansion, make sure to read the [lifecycle docs](https://docs.terragrunt.com/reference/hcl/blocks/#lifecycle).
